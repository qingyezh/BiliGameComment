# 三进程架构计划书（爬取 / 入库 / 前端）

版本：v1 · 状态：待实施  
范围：B 站游戏评论采集（主评论、不含楼中楼）性能与架构改造  
约束：单游戏串行翻页；限速硬下限 600ms + 抖动 0–200ms；队列采用目录文件（方案 A）

---

## 1. 背景与目标

### 1.1 背景

当前为单 Node 进程：`server.js` 同时承担控制台 API、翻页请求、JSONL 写入与偶发全表统计。  
入库/查询与爬取抢同一事件循环时，页速会低于「限速理论值」，且文件越大越明显。

### 1.2 目标

| 目标 | 说明 |
|------|------|
| 稳定页速 | 硬限速下稳定约 **1.25–1.5 page/s**（600–800ms/页） |
| 爬取不阻塞 | ③ 只请求 + 入队，不做重 IO / 全表扫 |
| 入库可恢复 | 队列落盘，崩溃后可继续消费，游标只推进已入库页 |
| 前端只读 | ① 刷新展示，不参与写库、不请求 B 站 |
| 可观测 | 页速、队列深度、入库延迟、session 增量可看 |

### 1.3 非目标

- 多游戏并行爬取  
- 同一游戏多连接并行翻页  
- 分析端大改（仍读 jsonl / 离线）  
- 楼中楼全文采集

## 2. 总体架构（三进程）

```text
┌────────────────────────────┐
│ ① server.js  前端/控制     │  端口 8787
│  静态页 · API · SSE        │
│  只读 data/ 与 runtime     │
│  start/stop → ③            │
└───────────┬────────────────┘
            │ 读状态 / 控制命令
            ▼
┌────────────────────────────┐    rename 入队     ┌─────────────────────────────┐
│ ③ crawl-daemon.js  爬取    │ ─────────────────▶ │ ② ingest-daemon.js  入库     │
│  签名 · 请求 · 限速        │  data/_queue/*.json │  落盘 jsonl · seen · 游标    │
│  仅投递页批次              │ ◀── 删文件即 ack ── │  fsync 节流 · 增量聚合       │
└────────────────────────────┘                    └─────────────────────────────┘
```

| 进程 | 入口（建议） | 职责 | 禁止 |
|------|----------------|------|------|
| ① 前端刷新 | `node server.js` | UI、查询/导出、SSE、启停转发 | 翻页、写评论、全表统计（默认） |
| ② 入库 | `node ingest-daemon.js` | 消费队列、写 `comments.jsonl`、seen、游标、节流 fsync、session 聚合 | 调用 B 站 API |
| ③ 爬取 | `node crawl-daemon.js` | `/game/comment/page` 请求、去重可选、入队、sleep | 写 jsonl、全库扫描 |

启动顺序：② → ③ → ①。

## 3. 限速规格

| 参数 | 值 |
|------|-----|
| 硬下限 `MIN_DELAY_MS` | **600** ms |
| 抖动 | **0–200** ms 均匀随机 |
| 单页间隔 | **600–800** ms（不含 HTTP RTT） |
| 理论吞吐 | **约 1.25–1.5 page/s** |
| `page_size` | 默认 20（接口上限） |
| 理论条速 | 约 25–30 条/s |

失败退避：1s → 2s → 4s → 8s；连续 8 页失败则停任务并写 error 状态。  
UI「间隔 ms」下限改为 **600**，默认 **600**。

## 4. 队列方案 A（目录丢文件）

### 4.1 目录

```text
data/_queue/          # ③ 写入、② 消费
data/_done/           # ② 处理成功后移入（便于排查；可定期清理）
data/_failed/         # 解析/落盘失败页，保留原文
```

### 4.2 文件命名

```text
{seq12位}-{gameId}-p{pageNum}.json
例：000000000123-103496-p42.json
```

`seq` 为进程内单调递增（可带时间戳后缀防重启冲突）。

### 4.3 消息体（单文件 = 一页）

```json
{
  "schemaVersion": 1,
  "gameId": "103496",
  "page": 42,
  "pageSize": 20,
  "rankType": 3,
  "paramsFingerprint": "rank3|ps20",
  "enqueuedAt": "2026-09-23T08:00:00.000Z",
  "items": [ { "...normalizeComment 字段...": "..." } ]
}
```

### 4.4 协议

1. **入队**：写 `*.json.tmp` → `fs.renameSync` 为 `*.json`（写完才算入队）。  
2. **出队**：② 按文件名排序取最旧；处理成功则 **移动** 到 `_done/`（或删除）。  
3. **失败**：解析/写库异常 → 移到 `_failed/`，记日志，不堵死队列。  
4. **背压**：③ 发现 `_queue` 内文件数 **&gt; 5** 则 sleep 200ms 再检查，最多等待后继续（仍受 600ms 限速约束）。  
5. **ack**：成功移入 `_done/` 即视为已消费；③ 不强制等待 ack，但 inflight（队列深度）受背压限制。

### 4.5 崩溃恢复

| 故障 | 行为 |
|------|------|
| ③ 崩溃 | ② 继续清空 `_queue`；重启 ③ 后从 ② 已写的游标续爬 |
| ② 崩溃 | ③ 背压暂停投递；重启 ② 后从 `_queue` 续消费 |
| ① 崩溃 | 不影响采集；重启后只读状态 |

**游标只由 ② 写**，且仅在「该页 items 已 append 完成」后，按 **连续页前缀** 推进 `lastCompletedPage`。

## 5. 数据与所有权

| 路径 | 写 | 读 |
|------|----|----|
| `data/<id>/comments.jsonl` | ② | ①、分析端 |
| `data/<id>/state/full.cursor.json` | ② | ①、③ 启动一次 |
| `data/<id>/state/update.cursor.json` | ② | ① |
| `data/<id>/state/seen.ids` | ② | ② 启动；③ 可选只读 |
| `data/<id>/state/grade-timeline.jsonl` | ②（或 ① 触发 ②） | ① |
| `data/<id>/runtime.crawl.json` | ③ | ① |
| `data/<id>/runtime.ingest.json` | ② | ① |
| `data/_queue/*` | ③ | ② |
| `config.local.json` | ①（保存配置） | ③ 启动读 Cookie |

去重：`comment_no` 的 Set 放在 **②**；③ 可只做页内去重，避免两份全量 Set。

## 6. 进程内要点

### ③ crawl-daemon.js

```text
启动 → 读 config/Cookie → 读 full.cursor 得 startPage
loop:
  若 queueDepth > 5: sleep
  fetchCommentPage(page)
  构造 items（normalize + crawled_at + source_page）
  enqueue 原子写入
  sleep(600 + random(0..200))
  写 runtime.crawl.json（page, rate, sessionNewEnqueue）
```

模式：`full_resume | full_restart | incremental`（增量仍支持重复窗口自动停）。

### ② ingest-daemon.js

```text
启动 → loadSeenIds → 扫 _queue
loop:
  取最小 seq 文件 → parse
  appendComments（可批量 flush）
  合并进 seen
  页完整后 writeCursor（节流 fsync：例如每 10 页或 3s）
  更新 runtime.ingest.json（queueDepth, flushed, seenCount, lag）
  均分采样每 10s（写 grade-timeline）
  移动到 _done/
```

### ① server.js

- `/api/crawl/start|stop`：写控制文件或调 ③ 本地控制口（实现期二选一，计划默认 **控制文件 `data/_cmd.json`** 以减少端口）  
- `/api/crawl/status`：合并 ③ + ② runtime  
- `/api/stats`：默认增量/聚合；`force=1` 才全表（且不在 ③ 热路径）  
- SSE：0.5s 级前端刷新只读上述文件

## 10. 验收标准

| 项 | 标准 |
|----|------|
| 页速 | 连续 10 分钟 **1.2–1.5 page/s**（网络正常时） |
| 队列深度 | 常态 0–3，不超过 5（背压生效） |
| 不重复 | `comment_no` 全局唯一 |
| 可恢复 | 杀掉 ② 或 ③ 后重启，能续跑且游标不越过未入库页 |
| 前端 | 采集时 UI 不拖慢页速；表单可编辑 |
| 限速 | 任意两次请求间隔 ≥ 600ms |

## 11. 风险与对策

| 风险 | 对策 |
|------|------|
| 600ms 触发风控 | 失败退避；可配置调回 800 |
| 磁盘队列碎片 | `_done` 定期清理；单页文件 |
| 游标乱序 | 仅连续页推进 lastCompletedPage |
| ③② 启动顺序错误 | ③ 启动检测 `_queue` 可写；② 无队列时 idle |

| 阶段 | 内容 | 产出 |
|------|------|------|

## 13. 一句话结论

采用 **「爬取 / 入库 / 前端」三进程 + 目录文件队列（方案 A）**，硬限速 **600ms**、抖动 **0–200ms**，使页速稳定在约 **1.25–1.5 page/s**，入库与刷新不再拖慢爬取，且崩溃可按队列与游标恢复。
